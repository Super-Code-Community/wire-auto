# Дизайн: `apps/deview` + двусторонний мост в `runtime/basic`

- Дата: 2026-08-17
- Статус: черновик на ревью
- Область: `apps/deview` (новый модуль), `runtime/basic` (правки), `guide/`

## 1. Цель

Дать платформе первый клиент — консольный `deview`: минимальный «браузер скриптов»
(нумерованное меню) + живое отображение хода выполнения. Для этого превратить
`runtime/basic` из разовой батч-команды в **двусторонний мост** между бекендом
приложения (`deview`) и скриптом.

## 2. Четырёхслойная модель (исходная логика)

Контракт течёт в две стороны:

```
        воля / заказ  ▼ вниз
  клиент ──▶ рантайм ──▶ ядро ──▶ скрипт
        ▲ вверх  годность / обещание
```

1. **Клиент** — заказывает запуск и рисует входящие данные; авторитет по форме
   данных/отрисовки (в v1 — единственный встроенный стандарт, см. §7).
2. **Рантайм** — часть бекенда клиента, вынесенная в модуль; приёмник ядер
   (допуск по контракту, не по имени); обслуживает клиента.
3. **Ядро** — определяет возможности скрипта и технологию вывода (живой поток /
   данные разом); самоопределяется для допуска наверх.
4. **Скрипт** — самоопределение-обещание следовать стандарту ядра.

Хребет слоёв 2–4 уже реализован (`registry`, `handshake`, `exec`, манифесты).
Недостающее — слой 1 (клиент) и верхняя граница как живой двусторонний канал.

## 3. Граница app↔runtime: протокол моста (JSON Lines)

Отдельная маленькая граница поверх stdio процесса `wire`. Не путать с протоколом
runtime↔script (`internal/protocol`) — это верхний контракт клиент↔рантайм.

**App → runtime (stdin):**

| type | поля | смысл |
|------|------|-------|
| `list` | — | запросить каталог скриптов |
| `run` | `dir` | запустить скрипт из папки |
| `cancel` | — | отменить текущий запуск (cancel→grace→kill) |
| `exit` | — | завершить мост (также по EOF stdin) |

**Runtime → app (stdout):**

| type | поля | смысл |
|------|------|-------|
| `catalog` | `scripts[]`: `name`, `dir`, `language`, `version`, `capabilities` | ответ на `list` |
| `ready` | — | скрипт поднялся |
| `log` | `level`, `message` | строка вывода скрипта (живьём) |
| `result` | `status`, `exitCode`, `errorCode`, `errorMessage`, `result?` | терминал запуска (+ опциональная нагрузка данных) |
| `error` | `message` | ошибка уровня моста (нет папки, битая команда) |

Одновременно выполняется **один** скрипт (минимально). Стриминг `log`
**необязателен**: «ядро, отдающее данные разом» присылает мало/ноль `log` и кладёт
данные в `result.result` — для клиента это та же последовательность, оканчивающаяся
`result`.

## 4. Правки в `runtime/basic`

`wire` — **всегда мост**. Разового прогона в CLI нет: процесс поднимается,
живёт «вечно» (продакшн-стиль) и обслуживает запуск за запуском на stdio, пока не
придёт `exit` или EOF stdin. Падение/ошибка одного скрипта **не роняет мост** —
прогон изолирован, наружу уходит `error`/`result`, мост продолжает слушать команды.

Go-функция `run()` (один прогон) сохраняется как **внутренний движок** — её зовут
мост и тесты (`main_test.go`), из CLI она напрямую больше не вызывается.

Изменения по пакетам:

1. **`internal/exec`**
   - `Run(ctx context.Context, spec Spec) Result` — внешняя отмена через `ctx`
     идёт в тот же путь cancel→grace→kill, что и таймаут.
   - `Spec.OnEvent func(Event)` (необязательный сток) — `ready`/`log` уходят
     наружу по ходу; при `nil` поведение как сейчас (только финальный `Result`).
   - `Result.Result json.RawMessage` — протащить нагрузку из `done.result`
     (сейчас теряется).
   - Новый статус `StatusCancelled = "CANCELLED"` для клиентской отмены.
2. **`internal/discovery`** (новый) — скан корня скриптов (по умолчанию `scripts/`)
   на `*/script.manifest`, возврат сводок для `catalog`. Переиспользует
   `manifest.LoadScript`. Симметрично сканированию `cores/`.
3. **`internal/bridge`** (новый, серверная сторона) — типы команд/событий +
   кодек JSON Lines; цикл: читать команды из `io.Reader` (stdin), диспетчеризовать
   (`list`→discovery, `run`→exec со стоком в поток событий, `cancel`→отмена
   `ctx` текущего прогона, `exit`/EOF→стоп).
4. **`cmd/wire/main.go`** — всегда поднимает мост на `os.Stdin`/`os.Stdout`
   (позиционного аргумента-скрипта больше нет). Флаги: `--runtime`, `--cores`,
   новый `--scripts` (корень discovery, по умолчанию `scripts`).

Обратная совместимость: `run()` не меняет контракт → e2e-тесты в `main_test.go`
(зовут `run()` напрямую) зелёные без правок.

## 5. Клиент `deview` (`apps/deview`)

Модуль `wire-auto/apps/deview`. Без TUI-фреймворка — REPL-цикл.

```
apps/deview/
├── go.mod                       module wire-auto/apps/deview
├── cmd/deview/main.go           точка входа: цикл меню
└── internal/
    ├── bridge/client.go         спавн `wire`, кодек протокола моста, интерфейс транспорта
    ├── ui/menu.go               нумерованный список из catalog
    └── ui/render.go             живой рендер событий + финальный блок result
```

**Поток:**
1. Старт → поднять `wire` (мост) фоном → `list` → `catalog` → нарисовать меню.
2. Ввод номера → `run{dir}` → рендер вживую: `ready`→«⏳ выполняется»,
   `log`→цветная строка по уровню, `result`→«✔ OK» / «✗ <status> (код)» +
   опциональный блок данных.
3. `Ctrl-C` во время прогона → `cancel` (не убивать `deview`) → назад в меню.
4. `q` → `exit` → чистое завершение.

**Поиск бинарника `wire`:** флаг `--wire` / env `WIRE_BIN`; dev-умолчание —
`go run ./runtime/basic/cmd/wire`. Транспорт за интерфейсом → тесты используют
in-memory фейковый мост.

**Регистрация модуля:** добавить `use ./apps/deview` в `go.work`.

## 7. Область v1 и что НЕ делаем

**В v1:**
- Один встроенный стандарт данных: живой поток `log` + опциональный `result`.
  Клиент его не выбирает, ядро не декларирует. Форматы/«тушки» поверх — забота
  будущих разработчиков.
- Один скрипт за раз в мосте (последовательно), но мост живёт неограниченно долго.
- Discovery — плоский скан `scripts/` на `script.manifest`.

**НЕ в v1 (признаём как будущее расширение — «вторая ось контракта»):**
- Декларация ядром output-режима в `core.manifest` и выбор клиентом формата в
  `run` со сведением в handshake.
- Параллельные прогоны в одном мосте.
- request/response к железу (зарезервировано протоколом).

## 8. Тестирование

- **Рантайм:** discovery (скан temp-папки); цикл моста (команды→ожидаемые события);
  стриминг `exec` (сток получает `log` до `result`); отмена (`ctx` → `CANCELLED`);
  протаскивание `result`-нагрузки. Существующие e2e-тесты — зелёные.
- **deview:** кодек моста (encode/decode); рендер меню из фейкового `catalog`;
  рендер прогона из скриптованного потока событий через фейковый транспорт.

## 9. Риски

- `wire` больше не разовая команда — пример запуска из `running.md` устаревает.
  Обновить доку: гонять скрипты через `deview` или пример с пайпом JSON-команд в
  stdin моста.
- Мост «вечный» → важна изоляция прогонов: паника/ошибка внутри одного `run` не
  должна ронять цикл моста (обернуть прогон, наружу отдавать `error`, продолжать
  слушать). Покрыть тестом «после провалившегося run мост принимает следующий».
- Отмена по `Ctrl-C` в клиенте требует перехвата SIGINT, чтобы слать `cancel`, а не
  убивать `deview` — держать простым, тестировать через фейковый транспорт.
