# port-scan → толстый Go-скрипт, скан всех портов

- **Дата:** 2026-08-17
- **Ядро:** `cores/duplex` (одна маленькая правка) + новый Go-скрипт
- **Статус:** дизайн утверждён, **план отложен на следующую сессию**

## Цель

Переделать демо-скрипт `scripts/examples/port-scan/` с Python на **Go** и заставить
его звонить **все порты 1–65535**. Скрипт становится «толстым»: он сам конкурентно
сканит порты через `net.Dial` в горутинах, не используя ядерную возможность
`net.tcp.connect`. Это обходит последовательный синхронный диспатч `exec.Run`
(65535 портов через per-port capability не влезут в `RunTimeout`) и показывает, зачем
вообще может понадобиться скрипт на компилируемом языке.

## Модель (утверждено)

**Толстый Go-скрипт** (не новая capability, не конкурентный диспатч ядра). Скрипт —
свой процесс с полным доступом к сокетам; тяжёлую работу он делает сам на Go, а с
ядром общается только по протоколу (lifecycle/log/result). Ядерные `net.*` для
этого скрипта не нужны.

## Ключевой факт запуска (проверено пробой)

При активном корневом `go.work` команда `go run .` в папке скрипта (модуль **не**
входит в workspace) падает:
> current directory is contained in a module that is not one of the workspace modules listed in go.work

С `GOWORK=off` — работает. Значит Go-скрипт обязан запускаться с `GOWORK=off`.
Манифест не несёт env, поэтому переменную выставляет ядро при спавне.

## Объём

### 1. Правка ядра (единственная, минимальная)

`cores/duplex/cmd/core/main.go`, функция `runStreaming`: добавить `"GOWORK=off"` в
слайс `Env`, передаваемый в `exec.Spec.Env` (рядом с существующим
`"WIRE_SDK_DIR=" + sdkDir`):
```go
Env: []string{"WIRE_SDK_DIR=" + sdkDir, "GOWORK=off"},
```
- Делает **любой** Go-скрипт герметичным (изолированным от dev-workspace).
- Для Python/Node безвредно: `GOWORK` — Go-переменная, ими игнорируется.
- `exec.Run` уже делает `cmd.Env = append(os.Environ(), spec.Env...)`; при дубле
  ключа побеждает последнее значение, так что `GOWORK=off` перекрывает возможный
  внешний `GOWORK`.

Больше в ядре ничего: `capreg`, `handshake`, `protocol`, мост, exec-цикл, deview — не трогаем.

### 2. Переписать `scripts/examples/port-scan/` как Go-модуль

Заменяем Python-версию (удаляем `main.py`). Новое содержимое папки:

- **`go.mod`** — самостоятельный модуль на stdlib (`net`, `encoding/json`, `os`,
  `bufio`, `time`, `sync`, `strconv`), без внешних зависимостей:
  ```
  module port-scan

  go 1.26
  ```
- **`scan.go`** — тестируемая конкурентная логика (без протокола):
  ```go
  func scanPorts(host string, ports []int, workers int, timeout time.Duration) []int
  ```
  Worker-pool: `workers` горутин тянут порты из канала, делают
  `net.DialTimeout("tcp", host:port, timeout)`; успех → порт открыт (закрыть conn).
  Возвращает отсортированный список открытых портов. Ошибка (отказ/таймаут) —
  просто «не открыт», не паника.
- **`main.go`** — протокол напрямую (как прежние duplex-скрипты, без SDK):
  `recv()` hello → `ready` → строит `ports = [1..65535]` → `open := scanPorts(...)`
  → лог по каждому открытому + итоговый лог → `done` с
  `result = {host, open:[...], scanned: 65535}`.
- **`script.manifest`:**
  ```toml
  name = "port-scan"
  version = "0.2.0"
  core = "duplex"
  coreApi = 1
  capabilities = []
  link = "stdio"
  language = "go"
  cmd = ["go", "run", "."]
  ```

**Параметры (константы в main.go):**
- `host = "127.0.0.1"` (скан localhost — как в прежней версии; ввод хоста — вне объёма, YAGNI).
- `ports = 1..65535`.
- `workers = 1000`.
- `timeout = 500 * time.Millisecond`.

Обоснование скорости: на localhost закрытые порты дают мгновенный refuse, открытые —
мгновенный connect, поэтому полный скан 65535 портов при 1000 воркерах занимает
секунды и укладывается в `RunTimeout` (60с). (Для полностью зафайрволенного удалённого
хоста время было бы `≈ (65535/workers)*timeout`; для localhost это не проявляется.)

**Логи:** не спамим — логируем каждый **открытый** порт и один итог
(`open ports: [...]` / `scanned 65535`). Закрытые/фильтрованные не логируются.

### 3. Тесты

- **Скрипт-модуль** (`cd scripts/examples/port-scan && GOWORK=off go test ./...`):
  `TestScanPorts` — поднять `net.Listen("tcp","127.0.0.1:0")` (открытый порт) и взять
  ещё один заведомо закрытый (слушать→узнать порт→закрыть); вызвать
  `scanPorts("127.0.0.1", []int{openPort, closedPort}, 8, 500ms)`; проверить, что
  открытый в результате есть, закрытого — нет. Малый набор портов, без реального
  скана 65k.
- **Ядро e2e** (`cores/duplex/cmd/core`): прогнать крошечный Go-testdata-скрипт через
  `runStreaming`/`bridge.Serve` и убедиться, что он стартует и отдаёт `result OK`.
  Это доказывает, что `GOWORK=off` проброшен (иначе `go run .` упал бы на go.work).
  Testdata: `cmd/core/testdata/gohello/` — минимальный Go-скрипт-модуль (`go.mod` +
  `main.go`), который делает `ready`+`done{ok:true}` (без сети — быстрый и
  детерминированный); `script.manifest` с `cmd=["go","run","."]`, `language="go"`.
- **Независимая сборка:** новый скрипт-модуль собирается сам
  (`cd scripts/examples/port-scan && GOWORK=off go build ./... && go vet ./... && go test ./...`);
  `cores/duplex` остаётся зелёным.

  сканящий все порты сам, без `net.tcp.connect`.

## Не трогаем

- `capreg`, реестр возможностей, `handshake`, `protocol`, мост, exec-цикл, deview.
- Ядерные `net.*` возможности (остаются для тонких скриптов; этот скрипт их не использует).

## Критерии готовности

1. `runStreaming` проставляет `GOWORK=off` в env скрипта; существующие e2e (python/node)
   по-прежнему зелёные.
2. `port-scan` — Go-модуль, сканит все 65535 портов на localhost конкурентно, отдаёт
   `result OK {host, open, scanned}`; проходит через ядро (ручная/e2e проверка).
3. `scanPorts` покрыт юнит-тестом (открытый найден, закрытый — нет).
4. Go-testdata-скрипт стартует через ядро (доказывает `GOWORK=off`-проводку).
5. Скрипт-модуль и `cores/duplex` собираются/вётятся/тестируются независимо.
6. Доки описывают Go-скрипты и обновляют пример port-scan.
